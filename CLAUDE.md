# TaskTrail — правила работы с проектом

TaskTrail — открытый self-hosted трекер задач для небольших команд, без долгой настройки.
Сервер — Go (`server/`), веб-клиент — React и TypeScript (`web/`). Проект разрабатывают
AI-агенты (Claude): код пишет и проверяет агент, владелец проекта — заказчик: ставит задачи
и принимает результат. Правила ниже обязательны: они держат контекст проекта под контролем.

## Принципы

Изменить принципы может только заказчик, и только новым ADR.

1. **Лёгкий трекер** ([ADR-0004](docs/adr/0004-lightweight-tracker-scope.md)). Поля и статусы
   задач фиксированы; настраиваемых полей, workflow-скриптов, учёта времени и языка запросов нет.
2. **Self-hosted и открытый.** Лицензия MIT. Всё поднимается на своей машине. Внешние сервисы
   должны подключаться по желанию: в разработке почта уходит в локальный перехватчик
   ([ADR-0010](docs/adr/0010-local-development.md)). Сейчас сервер ещё требует настроек SMTP.
3. **Контракт API — источник истины** ([ADR-0005](docs/adr/0005-monorepo-api-contract.md)).
   Сервер и клиент меняются вместе с контрактом в одном PR.
4. **Настройки — в интерфейсе** ([ADR-0015](docs/adr/0015-settings-in-admin-ui.md)). Сервис
   и интеграции настраивает администратор в интерфейсе; в переменных окружения — только то,
   без чего сервер не запустится.

  следуй им, пока он не решил иначе.

## Когда нужен ADR

ADR нужен, если изменение:

- добавляет или заменяет библиотеку или часть стека;
- меняет модель данных или контракт API: новые таблицы и поля, смысл существующих, эндпоинты;
- меняет доступ и безопасность: авторизацию, роли, хранение секретов и токенов;
- меняет структуру репозитория или подход: слои, работу с состоянием, обработку ошибок;
- меняет проверки, CI или выпуск;
- отменяет принятое решение или отступает от него.

ADR не нужен для исправления ошибок, правок интерфейса, функций в рамках принятых решений,
рефакторинга без смены подхода и обновления версий без изменения поведения.

Правило, которое агент без подсказки нарушит или переизобретёт, запиши — место выбирай по охвату:
правило одного экрана, компонента или функции — в комментарии к этому коду; правило для многих
мест, для данных или для того, чего в коде ещё нет, — в ADR.

Решение, о котором заказчик не просил, сначала согласуй с ним: ADR со статусом «Предложено».
Как писать ADR — `docs/adr/template.md`. Принятый ADR по существу не переписывается: чтобы
изменить решение, напиши новый ADR с полем «Заменяет», а старому поставь статус «Заменено».
Без нового ADR можно исправить опечатки и переехавшие пути, уточнить «Затрагивает», дописать
«Проверку» и перенести правило одного экрана или функции в комментарий к коду, оставив в ADR ссылку.

## Когда обновлять README

README пишется для людей. Обнови его, если изменение заметно пользователю или разработчику:
возможности, запуск и настройка, локальный стенд, проверки. У каждой интеграции с внешним
сервисом (почта и следующие) в README есть подраздел: что она делает; какие данные, куда
и когда уходят с сервера; как её включить, настроить и отключить. Объяснение «почему так» —
в ADR, README на него ссылается.

## Сборка и проверка

- Задача не считается выполненной, пока не проходит `scripts/dev.sh check` и не зелёный CI
  в её PR ([ADR-0009](docs/adr/0009-checks-and-ci.md)). `check` — правила проекта
  (`scripts/dev.sh rules`), сервер (vet, тесты с проверкой ответов по контракту, golangci-lint)
  и веб (сверка типов API с контрактом, линтер, тесты, типы, сборка).
- Нужны Go (версия — `server/go.mod`), Node.js (версия — `engines` в `web/package.json`) и, для стенда
  и интеграционных тестов, Docker.
  Docker Desktop агент запускает сам, когда он нужен.
- Локальный стенд — `scripts/dev.sh up|smoke|down|reset|logs`; что на нём работает и как войти —
  README, «Локальный стенд». После `up` прогони `smoke`.
- ИИ-ревью (скилл `/code-review`) запускает заказчик, когда сочтёт нужным; при сдаче задачи
  агент его сам не запускает.

## Ветки и PR

- Каждая задача — своя ветка от свежего `origin/main`: локальный `main` отстаёт, пока его
  не обновят. Параллельная сессия работает в отдельном worktree: `git fetch`, затем
  `git worktree add ../task-trail-<задача> -b <ветка> origin/main`.
- Когда PR слит, убери его worktree: `scripts/dev.sh cleanup` удаляет папки и ветки всех слитых
  PR — исходники остаются в истории git. Папку с незакоммиченными правками команда не трогает.
  Временный worktree (проба, проверка слияния) убери сразу после проверки: `cleanup` его не видит.
- Прежде чем открывать PR, покажи результат заказчику: что поменялось и где это посмотреть
  на локальном стенде (`scripts/dev.sh up`, [ADR-0010](docs/adr/0010-local-development.md)).
  До этапа 1 на стенде работает эталон старого API, а не `server/`: изменения сервера показывай
  тестами и выводом `scripts/dev.sh check`. PR — только после его «да».
- В `main` изменения попадают только через PR (`gh pr create`). Сливает PR заказчик, агент —
  только по его просьбе и при зелёном CI, по скиллу `/merge`.
- Результат CI читай кратко: `gh pr checks`, при падении — `gh run view <id> --log-failed`.
  Упавший шаг повтори локально той же командой `scripts/dev.sh`; полный лог не скачивай.
