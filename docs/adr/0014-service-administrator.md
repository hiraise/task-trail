# ADR-0014: Сервисом управляет администратор сервиса

- **Статус:** Принято
- **Дата:** 2026-10-21
- **Затрагивает:** таблица `users` в `server/migrations/`, проверки доступа в `server/internal/`, `server/internal/presentation/http/v1/`, `server/internal/presentation/http/router.go`, раздел администратора в `web/src/presentation/features/`, администрирование в контракте API

## Контекст

Настройки и интеграции задаются в интерфейсе ([ADR-0015](0015-settings-in-admin-ui.md)), а без
почты пароль восстанавливают через человека. Нужна роль, которой это доступно; роли проекта
([ADR-0003](0003-fixed-roles-and-statuses.md)) для этого не подходят.

## Решение

- Администратор сервиса — признак `users.is_admin`. Роли проекта (ADR-0003) он не меняет
  и доступа к чужим проектам не даёт.
- Первый аккаунт ([ADR-0016](0016-invite-only-signup-first-admin.md)) создавай администратором.
- Администратор назначает и снимает администраторов. Последнего администратора снять нельзя:
  проверку и снятие делай под `pg_advisory_xact_lock`, иначе два встречных снятия оставят
  сервис без администраторов.
- Администратору доступны настройки и интеграции сервиса и список пользователей; для любого
  пользователя он получает ссылку сброса пароля.
- Права администратора проверяй на сервере в каждом эндпоинте администрирования; веб только
  прячет раздел.
- Документацию API (Swagger) отдавай всегда, но только администратору; переменные `SWAGGER_*`
  удали.

## Последствия

- Через ссылку сброса администратор может войти в любой аккаунт — как и тот, у кого есть доступ
  к серверу и базе. Для self-hosted это ожидаемо.
- Блокировка пользователей и обзор всех проектов — позже, отдельным ADR.
