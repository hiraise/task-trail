# TaskTrail

Открытый self-hosted трекер задач для небольших команд: проекты, участники с ролями, задачи,
комментарии, канбан-доски и поиск, без многодневной настройки.

Проект в разработке. Этап 3 закрыт: кроме ядра трекера — ключей задач, архива, комментариев
с историей, досок и поиска — на локальном стенде работают приоритет, срок, метки, подзадачи,
вложения, уведомления с письмами и напоминаниями, упоминания в комментариях. Его можно установить
на свой сервер из готовых образов — «Установка на свой сервер» ниже. В планах — права
администратора сервиса над проектами ([docs/roadmap.md](docs/roadmap.md)).

## Структура

| Путь | Что там |
| --- | --- |
| `api/openapi.yaml` | Контракт API (OpenAPI 3.1) — источник истины для сервера и веба; сервер встраивает его для Swagger (`api/openapi.go`) |
| `server/` | API на Go (Gin, PostgreSQL); история перенесена из `hiraise/tt-backend` |
| `web/` | Веб-клиент на React и TypeScript (Vite); история перенесена из `hiraise/tt-frontend` |
| `docs/adr/` | Архитектурные решения — [индекс](docs/adr/README.md) |
| `stand/` | Локальный стенд в Docker: compose-файл |
| `deploy/compose.yaml` | Установка на свой сервер из готовых образов |
| `scripts/dev.sh` | Проверки и управление стендом |
| `CLAUDE.md` | Правила работы для AI-агентов |

## Установка на свой сервер

Каждая версия — git-тег `vX.Y.Z` на `main`: CI ставит его сам, когда ветка релиза `release/X.Y.Z`
вливается в `main`, собирает образы `ghcr.io/hiraise/task-trail-server`
и `ghcr.io/hiraise/task-trail-web` (`linux/amd64`) с тегами `X.Y.Z` и `latest` (последний релиз)
и публикует релиз на GitHub с описанием изменений и файлом `deploy/compose.yaml`
([ADR-0042](docs/adr/0042-release-images-and-compose.md), [ADR-0043](docs/adr/0043-release-branches.md)).

`deploy/compose.yaml` — PostgreSQL, сервер и веб; наружу открыт только порт веба (`TASKTRAIL_PORT`,
по умолчанию 3000), веб сам проксирует `/api` на сервер. Перед ним нужен HTTPS-прокси: cookie
сессии передаются только по защищённому соединению, без HTTPS войти нельзя. Переменные — в `.env`
рядом с `deploy/compose.yaml` или в окружении `docker compose`:

| Переменная | Пример | Что задаёт |
| --- | --- | --- |
| `APP_SECRET` | `openssl rand -hex 32` | ключ подписи сессий и шифрования секретов настроек |
| `POSTGRES_PASSWORD` | `openssl rand -hex 24` | пароль базы: только буквы и цифры |
| `TASKTRAIL_PORT` | `3000` (по умолчанию) | порт веба на хосте |
| `TASKTRAIL_VERSION` | `latest` (по умолчанию) | версия образов; `1.0.0` — закрепить или откатиться |

`APP_SECRET` и `POSTGRES_PASSWORD` сохраните вне сервера: они нужны для восстановления из бэкапа.

```bash
docker compose -f deploy/compose.yaml up -d                                         # первый запуск
docker compose -f deploy/compose.yaml pull && docker compose -f deploy/compose.yaml up -d   # обновление
```

После первого запуска сразу откройте сайт и зарегистрируйтесь: первый аккаунт становится
администратором сервиса, и пока его нет, занять его может любой, кто открыл сайт
([ADR-0016](docs/adr/0016-invite-only-signup-first-admin.md)). Затем в разделе администратора
укажите адрес сервиса и подключите почту (раздел «Почта» ниже).

Миграции базы сервер применяет сам при старте. Откат — `TASKTRAIL_VERSION` с прошлой версией:
код откатывается, база — нет; если новая версия уже применила миграцию, поможет бэкап. Изменения
`deploy/compose.yaml` и новые обязательные переменные названы в описании релиза.

### Бэкап

Бэкап — это вместе тома `database` и `files` стека и `APP_SECRET`: с другим ключом все сессии
закончатся, а пароль почты придётся ввести заново. Если администратор потерял доступ, а почта
не подключена, ссылку сброса пароля печатает сервер: в контейнере `server` — команда
`./app password-reset-link <email>` ([server/README.md](server/README.md), «Commands»).

## Разработка

Нужны Go (версия — в `server/go.mod`), Node.js (версия — `engines` в `web/package.json`) и Docker.

```bash
scripts/dev.sh check    # всё, что проверяет CI: правила, сервер, веб
scripts/dev.sh server   # только сервер: vet, тесты, golangci-lint
scripts/dev.sh web      # только веб: типы API из контракта, линтер, тесты, типы и сборка
scripts/dev.sh ci 42    # дождаться CI пулл-реквеста 42 (или ветки: main, release/1.1.0) и вывести итог; при падении — лог до первой ошибки
scripts/dev.sh images 1.0.0   # собрать образы релиза локально; CI собирает и публикует их при выпуске релиза
```

Разработка идёт релизами ([ADR-0043](docs/adr/0043-release-branches.md)). Под версию от `main`
открывается ветка `release/X.Y.Z`; каждая задача — своя ветка от неё и пулл-реквест в неё. Готовый
релиз — пулл-реквест `release/X.Y.Z` → `main`: его описание открывает заметки к релизу. После
вливания CI сам ставит тег `vX.Y.Z`, собирает образы и публикует релиз; на сервере остаётся скачать
новые образы («Установка на свой сервер»). В `main` попадают только ветки релизов — CI отклоняет
остальные пулл-реквесты, а обновления Dependabot перед вливанием переводятся на ветку релиза.
Срочное исправление — тоже релиз: ветка `release/X.Y.Z+1` от `main`.

Переменные окружения сервера — в [server/README.md](server/README.md), веба — в [web/README.md](web/README.md).

В VS Code те же команды — в Terminal → Run Task: стенд, проверка, правила проекта
([.vscode/tasks.json](.vscode/tasks.json)).

Каждая задача — своя ветка и, если сессий несколько, свой `git worktree` рядом с репозиторием.
`scripts/dev.sh cleanup` убирает worktree и ветки, чьи PR уже слиты. Обновления зависимостей
раз в неделю предлагает Dependabot ([ADR-0021](docs/adr/0021-dependabot-updates.md)).

## Локальный стенд

```bash
scripts/dev.sh up       # собрать, запустить и настроить пустую базу; на macOS сам запускает Docker Desktop
scripts/dev.sh smoke    # дымовая проверка: вход, приглашение по письму, задача с ключом, комментарием, историей, архивом, приоритетом, сроком, меткой, подзадачей и вложением, уведомление о назначении, аватарка
scripts/dev.sh logs     # логи всех сервисов, или одного: logs server
scripts/dev.sh down     # остановить, база и файлы сохраняются
scripts/dev.sh reset    # остановить и стереть базу и файлы
scripts/dev.sh screens out /tasks   # скриншоты стенда на 393, 768 и 1200 px под администратором; Playwright скачивается в .cache/
```

| Адрес | Что там |
| --- | --- |
| http://localhost:3000 | веб-клиент; API — тот же адрес, путь `/api` |
| http://localhost:3025 | перехватчик почты Mailpit: письма приглашений и сброса пароля |
| http://localhost:3000/api/docs/ | Swagger сервера — после входа администратором в веб, в том же браузере |

Вход — `admin@tasktrail.local`, пароль `tasktrail`. Это первый аккаунт, администратор сервиса:
на пустой базе `up` создаёт его с адресом сервиса `http://localhost:3000` и подключает почту
к Mailpit через API администратора, как это сделал бы администратор в интерфейсе
([ADR-0015](docs/adr/0015-settings-in-admin-ui.md)). После этого регистрация закрыта: новых
пользователей зовут в проект, ссылка приглашения приходит в Mailpit. Что поменяли в настройках
на стенде, `up` не трогает; вернуть всё как было — `reset` и `up`.

Открывайте в Chrome или Firefox: сервер ставит cookie с флагом `Secure`, а Safari не принимает
их по `http`.

Стенд один на машину: `up` из любого worktree пересобирает его из своих `server/` и `web/`,
а `reset` стирает общую базу. С переходом на сервер из `server/` база стенда лежит в новом томе
`tasktrail_database` и начинается пустой: схема старого API новому серверу не подходит. Прежние
тома больше не нужны: `docker volume rm tasktrail_postgres tasktrail_pgdata`.

Сервер на стенде реализует весь контракт `api/openapi.yaml`, веб работает с ним по контракту.
Работают вход и выход, регистрация первого аккаунта на пустой базе, принятие приглашения по ссылке
из письма, восстановление и сброс пароля, профиль: имя, аватарка, смена пароля. Проекты и участники:
создание проекта с приглашениями, изменение, удаление и выход, приглашение, смена роли и исключение
участника — действия в меню видны по роли в проекте. У проекта есть ключ, например `DS`: форма
нового проекта предлагает его по названию, менять ключ может только владелец
([ADR-0026](docs/adr/0026-project-and-task-keys.md)). Задачи: «Мои задачи», задачи проекта, создание
(со страницы проекта — сразу в этом проекте), изменение и удаление, смена статуса и ответственного,
перенос в другой проект. У каждой задачи ключ вида `DS-12`: номер идёт по порядку внутри проекта,
при переносе задача получает следующий номер нового проекта. Проектам, созданным до ключей,
миграция дала ключи `P1`, `P2`… — владелец может их сменить. Архив
([ADR-0027](docs/adr/0027-reversible-archive.md)): задачу может убрать в архив любой участник
проекта, проект — только владелец; из архива их можно вернуть. Архивные задачи и проекты — только
для чтения, они лежат на вкладке «Архивные» в «Мои проекты», «Мои задачи» и в задачах проекта.
Под задачей — лента ([ADR-0028](docs/adr/0028-task-activity-feed.md)): комментарии и история
изменений вперемешку, новые сверху. Комментарий пишет любой участник проекта, ссылки в нём
кликабельны; автор может изменить его в первые 24 часа, удалить — автор, владелец или
администратор проекта. История показывает создание задачи, смену статуса и ответственного,
перенос, изменение названия или описания, архив и возврат. Комментарии архивной задачи — только
для чтения. Задачам, созданным до ленты, миграция записала событие «Задача создана».
Доски ([ADR-0029](docs/adr/0029-boards-over-projects.md)) собирают задачи нескольких проектов:
доску создаёт любой пользователь, выбирает свои проекты и участников — тех, с кем у него есть
общий проект. Участие в доске не даёт доступа к задачам: каждый видит на доске только проекты,
где он сам участник, и их активные задачи, у которых ответственный — участник доски или никто.
Владелец переименовывает доску, меняет проекты и участников, удаляет её (задачи остаются);
участник может покинуть доску. Доска — канбан: колонки по статусам, строки по участникам доски
и «Без ответственного» (у доски с одним участником строк нет). Строку можно свернуть — браузер
это запомнит. Карточку перетаскивают в другую колонку (меняется статус) или строку (меняется
ответственный, только участник проекта задачи); на телефоне — долгим нажатием. «Создать задачу»
в ячейке создаёт задачу сразу в её статусе и с ответственным этой строки. Карточка открывает
задачу: от 1024 px — поверх доски, уже — на отдельной странице; ключ задачи всегда ведёт на её
страницу.
Поиск ([ADR-0030](docs/adr/0030-search-by-substring.md)) ищет подстроку без учёта регистра
в названиях проектов, досок и задач, в описаниях задач и в ключах вроде `DS-12` — только среди
того, что пользователь и так видит. Результаты — до 20 в группах «Проекты», «Доски», «Задачи»,
группы сворачиваются, совпадения подсвечены, архивные проекты и задачи помечены «Архив».
Запрос уходит через 300 мс после ввода и сохраняется в адресе страницы: «Назад» из найденной
задачи возвращает к тем же результатам.
У задачи есть приоритет — срочный, высокий, обычный (по умолчанию) или низкий
([ADR-0033](docs/adr/0033-task-priority.md)), и необязательный срок — день календаря; просроченная
задача помечена красным ([ADR-0034](docs/adr/0034-task-due-date.md)). Метки — свои у каждого
проекта, с цветом из палитры: создать метку может любой участник, переименовать, перекрасить и
удалить — владелец и администраторы проекта, у задачи до 10 меток
([ADR-0035](docs/adr/0035-project-labels.md)). Подзадача — задача проекта с родителем, один уровень
вложенности; на карточке родителя — прогресс «2/5» ([ADR-0036](docs/adr/0036-subtasks.md)).
К задаче прикладывают файлы до 25 МБ, у картинок есть превью; скачать их могут только участники
проекта ([ADR-0037](docs/adr/0037-task-attachments.md)). Колокольчик со счётчиком показывает
уведомления: назначение ответственным, смена статуса, комментарий, упоминание, скорый и
пропущенный срок ([ADR-0038](docs/adr/0038-notifications.md)). В комментарии после «@» поле
предлагает участников проекта; упомянутый получает уведомление, а в комментарии имя подсвечено
([ADR-0039](docs/adr/0039-comment-mentions.md)).
Списки сортируются по дате обновления, дате создания, по алфавиту, по приоритету или по сроку;
выбор запоминается в браузере. Раздел администратора (в боковом меню, на телефоне — из профиля): адрес
сервиса, почта, пользователи — назначить администратора, письмо или ссылка сброса пароля.
То, чего не показывает веб, проверяется в Swagger.

## Интеграции

Внешние сервисы подключаются по желанию: без них TaskTrail работает.

### Почта

Сервер шлёт письма со ссылками: сброс пароля, приглашение в проект тому, у кого ещё нет аккаунта,
и извещение тому, кого добавили в проект сразу, — а также письма об уведомлениях (ниже).

Письмо уходит только на SMTP-сервер, который подключил администратор сервиса. Письмо со ссылкой
уходит в момент запроса, которому оно нужно, например «Забыли пароль?» или приглашение в проект: адрес получателя,
тема и текст — имя пригласившего, название проекта, ссылка на веб. Токен в ссылке сброса
одноразовый, в базе хранятся только хеши токенов. Пароль SMTP лежит в базе
зашифрованным ключом из `APP_SECRET` и уходит только на сервер и порт, для которых его ввели.

Включает почту администратор: сохраняет сервер SMTP, порт, шифрование (нет, STARTTLS или TLS),
отправителя и, если нужно, логин и пароль; там же меняет и отключает. Перед сохранением сервер
подключается к SMTP с этими настройками, входит и спрашивает, примет ли SMTP письмо от этого
отправителя, — само письмо не уходит; не вышло — настройки не сохраняются. Проверить доставку
администратор может тестовым письмом себе. Всё это — в разделе «Администрирование» веба, карточка
«Почта»; отключение там же удаляет настройки SMTP и пароль.

С почтой администратор может отправить пользователю письмо для сброса пароля из списка
пользователей — то же письмо, что по «Забыли пароль?». Без почты «Забыли пароль?» отвечает, что
почта не подключена: ссылку сброса выдаёт администратор в том же списке (ссылка нужна и с почтой,
если человек потерял доступ к ящику), а тому, кто управляет сервером, — команда `password-reset-link` ([server/README.md](server/README.md)).
Ссылку приглашения без почты пригласивший получает в ответе и передаёт сам: веб показывает её
после приглашения с кнопкой «Скопировать». Если письмо приглашения не ушло, веб так и пишет
и предлагает пригласить снова — уйдёт новое письмо. Почему так —
[ADR-0017](docs/adr/0017-mail-in-admin-ui.md).

Письма об уведомлениях повторяют колокольчик веба: назначение ответственным, смена статуса,
комментарий к задаче, где человек автор или ответственный, упоминание в комментарии, а ответственному —
напоминание за день до срока и на следующий день после него. Письмо получает только тот, кому
адресовано уведомление, и только если он не прочитал его за 5 минут: фоновая задача раз в минуту
отправляет непрочитанные уведомления старше 5 минут и моложе суток, каждое — одним письмом и один раз.
Из сервера уходят адрес получателя, ключ и название задачи, имя автора изменения, начало комментария
(до 200 символов) и ссылка на задачу. Человек выключает такие письма у себя в профиле («Письма об уведомлениях»); отключение
почты администратором останавливает все письма. Почему так —
[ADR-0038](docs/adr/0038-notifications.md).

## План

Подробно — [docs/roadmap.md](docs/roadmap.md). Документы для агентов написаны по-английски
([ADR-0031](docs/adr/0031-english-agent-docs-and-stage-plans.md)).

1. **Этап 0 — закрыт.** Единый репозиторий, правила и ADR, проверки и CI, локальный стенд.
2. **Этап 1 — закрыт.** Контракт API в `api/openapi.yaml`, сервер, который его реализует, и веб на нём.
3. **Этап 2 — закрыт.** Комментарии, доски, поиск, архив, ключи задач — ядро из [ADR-0004](docs/adr/0004-lightweight-tracker-scope.md).
4. **Этап 3 — закрыт.** Приоритет, срок, метки, подзадачи, вложения, уведомления и упоминания —
   «после ядра» из [ADR-0004](docs/adr/0004-lightweight-tracker-scope.md).
